# FlashVSR Roofline 性能分析报告：480p → 1080p（Xeon AMX）

> 目标场景：在 **8 个 Xeon 物理核** 上，使用 **AMX-BF16** 指令集，对 **480p 输入进行超分（SR）得到 1080p 输出**，评估可达帧率（FPS）。
> 方法：Roofline 模型（算力屋顶 vs 内存带宽屋顶），参数取自本仓库源码（`diffsynth/models/wan_video_dit.py`）。

---

## 1. 执行摘要（TL;DR）

| 配置（8 物理核） | 每帧耗时 | **可达 FPS** |
|------------------|:---:|:---:|
| FP32（不用 AMX） | ~6.1 s | ~0.16 FPS |
| **AMX-BF16 可持续（~7 TFLOPS）** | **~0.9 s** | **~1.1 FPS** |
| AMX-BF16 乐观（~11 TFLOPS） | ~0.6 s | ~1.8 FPS |
| AMX-BF16 峰值（~15 TFLOPS） | ~0.4 s | ~2.4 FPS |

**核心结论：480p→1080p 在 8 个 Xeon 核 + AMX-BF16 下约 `1.1 FPS`（现实可持续值），乐观调优可达 ~1.8 FPS。** 该负载为**计算受限（compute-bound）**，性能完全由 AMX 算力决定，AMX 相对纯 FP32 带来约 **7×** 提升，是达到 1 FPS 目标的决定性因素。

## 2. 场景定义

| 项 | 值 | 来源/说明 |
|----|----|----------|
| 任务 | 视频超分（SR），一步扩散 | `num_inference_steps=1` |
| 输入 | 480p（≈854×480） | SR 输入 |
| 输出 | **1080p → 对齐为 1920×1088** | 源码要求分辨率为 128 的整数倍（`compute_scaled_and_target_dims`, `multiple=128`），1080 → 1088 |
| 计算量决定因素 | **输出分辨率** | DiT 在输出潜空间尺寸上运行，故 FLOPs 由 1080p 输出决定，而非 480p 输入 |
| 硬件 | 8 个 Xeon 物理核（SPR/EMR，支持 AMX） | — |
| 数据类型 | BF16（AMX 原生） | — |

| 参数 | 值 |
|------|----|

## 4. 计算量（FLOPs）分析

### 4.1 每 token 每层线性算力
```
lin_per_token = 2 × (4·dim² [自注意力 QKVO] + 4·dim² [交叉注意力] + 2·dim·ffn [FFN])
              ≈ 2 × (9.4M + 9.4M + 27.5M) ≈ 92 MFLOP/token/层  (含 ×2 MAC)
```

### 4.2 输出 1080p（1920×1088）每帧 FLOPs

| 分辨率 | token/帧 | 线性 | 注意力(稀疏15%) | **合计/帧** |
|--------|:---:|:---:|:---:|:---:|
| 输入 480p（854×480） | 1590 | 1107 G | 17 G | 1124 GFLOP |
| **输出 1080p（1920×1088）** | **8160** | **5679 G** | **460 G** | **≈6140 GFLOP/帧** |
| （参考）稠密注意力 | 8160 | 5679 G | 3068 G | ≈8747 GFLOP/帧 |

> **关键**：计算量由**输出 1080p** 决定（6.14 TFLOP/帧）。若注意力退化为稠密（未实现真稀疏算子），注意力从 460→3068 GFLOP，总量增至 8.75 TFLOP/帧，FPS 再降约 30%。

---

## 5. Roofline 判定：计算受限还是内存受限？

**两把尺子（8 物理核）：**
- 计算屋顶：AMX-BF16 可持续 **~7 TFLOPS**（峰值 ~15）
- 内存屋顶：8 核可用带宽 **~150 GB/s**
- **脊点（ridge point）= 7000 / 150 ≈ 47 FLOP/byte**

**工作点算术强度：**
- 权重仅 2.8GB，一步推理中权重高度复用（长驻 cache）；FFN(1536↔8960) 为大 GEMM。
- 估算 **AI ≈ 1000–2400 FLOP/byte ≫ 脊点 47**。

```
   性能
   (FLOPS)
  7T ┤------------------------●═══════════  ← 计算屋顶 (AMX-BF16)
     │                   ╱    ↑
     │              ╱         工作点 AI≈1000+
     │         ╱ (带宽屋顶)   (远在脊点右侧)
     │    ╱
     └────┴──────────────────┴──────────►  算术强度 (FLOP/byte)
        脊点47              1000+
```

> **结论：FlashVSR 属于彻底的计算受限（compute-bound）负载。** 提升 FPS 的唯一有效杠杆是**堆算力（AMX-BF16）**，而非优化访存。内存带宽不是瓶颈。

---

## 6. FPS 预测（8 物理核，输出 1080p，真稀疏注意力）

`FPS = 可达算力 / 每帧FLOPs(6.14 TFLOP)`

| 执行路径 | 可达算力 | 每帧耗时 | **FPS** |
|----------|:---:|:---:|:---:|
| FP32（无 AMX） | ~1.0 TFLOPS | 6.1 s | 0.16 |
| **AMX-BF16 可持续** | **~7 TFLOPS** | **0.9 s** | **~1.1** |
| AMX-BF16 乐观调优 | ~11 TFLOPS | 0.6 s | ~1.8 |
| AMX-BF16 峰值（理论上限） | ~15 TFLOPS | 0.4 s | ~2.4 |

**交叉验证**：A100 实测 17 FPS@768×1408，反推有效算力 ≈51 TFLOPS（≈A100 峰值 16%），是合理的真实利用率，佐证上述每帧 FLOPs 量级可信。

---

## 7. 达标前提与优化建议

要稳定达到 **~1 FPS 及以上**，以下缺一不可：

1. **走 AMX-BF16 路径（决定性，7× 提升）**
   - 用 Intel Extension for PyTorch：`ipex.optimize(model, dtype=torch.bfloat16)`，或依赖 oneDNN 自动调度 AMX。
2. **真稀疏注意力算子（大尺寸决定性）**
   - LCSA 的掩码逻辑源码已实现（纯 PyTorch）；只需把 `block_sparse_attn_func` 这一 CUDA 算子替换为 CPU「真稀疏」实现（按现成 mask 只算保留块），避免稠密退化使 FPS 腰斩。
3. **分块推理 `tiled=True`（稳定性）**
   - 源码已支持。把每块钉在 512² 内（1080p 约需 12 块，每块 ~720 GFLOP），单块注意力恒定小，利用率更高、显存/cache 更友好。
4. **Tiny 管线 + TCDecoder**：解码远轻于 Wan2.1 VAE，省端到端时间。
5. **8 核 NUMA 绑定 + 线程调优**：`numactl` + `OMP_NUM_THREADS`，把可持续算力顶到 ~7 TFLOPS，额外 20–50%。

---

## 8. 敏感性分析

| 变量 | 影响 |
|------|------|
| AMX vs FP32 | **~7×**（最大杠杆） |
| 真稀疏 vs 稠密注意力 | 1080p 下约 **1.4×**（460 vs 3068 GFLOP 注意力） |
| 输出分辨率 768×1408 → 1080p | 像素 ~1.9× → FPS 减半（2.3 → 1.1） |
| 核数 8 → 16 | 近线性 → FPS 约翻倍（若带宽不成为新瓶颈） |
| INT8 量化（AMX-INT8） | 峰值再 ~2×，但需评估画质，扩散模型需谨慎 |

---

## 9. 结论

- **480p→1080p 的 FlashVSR，在 8 个 Xeon 物理核 + AMX-BF16 下，可达约 `1.1 FPS`（可持续），调优乐观区间 `1.1–1.8 FPS`。**
- 负载为**计算受限**，AMX 是达标关键（相对 FP32 提升约 7×）；纯 FP32 仅 ~0.16 FPS，无法达标。
- 满足「AMX-BF16 + 真稀疏注意力 + 分块 + NUMA 调优」四项前提后，**1 FPS 目标可稳定达成**，并对之前设定的 0.5 FPS（2s/帧）有充足余量。
